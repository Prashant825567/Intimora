# Intimora

Intimora is a React + Vite frontend designed to run as a **Render Static Site**. The browser calls the public discovery Worker, reads `data.server` (and `data.php`) from `{ "ok": true, "data": { "server": "https://…", "php": false } }`, and calls that backend directly, appending routes such as `/api/videos`. Nothing is proxied: the browser is the only client of the backend, including when that backend is a PHP host behind a free-hosting browser check (see [PHP host behind a free-host check](#php-host-behind-a-free-host-check-direct-cookies)).

## Discovery and routing

The existing public Worker is the default. To use a different public endpoint, set `INTIMORA_PUBLIC_API_DISCOVERY_URL` at **build time** (see `.env.example`). It must be an HTTPS URL without credentials, a query string, or a fragment. The build rejects invalid values without printing them. The variable and Worker URL are public, not secrets.

Discovery starts on arrival, including while the age gate is open. Each new browser tab/navigation starts its own discovery; concurrent requests in that tab share it. The selection is cached for at most 60 seconds from the start of discovery, using session storage with an in-memory fallback. Reloading the same tab may reuse its own unexpired selection. A new navigation does not reuse an entry copied from another tab. When it expires, the next request refreshes discovery; videos and pagination cursors already loaded remain pinned to their original backend. Media elements contact that backend directly and support its byte-range responses. Likes and share tracking also use the video's original backend.

Home carries one filter bar directly under the hero and above the "All Videos" heading: **All**, **Desi**, **Anime**, **Sponsored** and **Premium** (Premium sits right beside Sponsored). It filters the same catalogue in place — home keeps one address, one title and one heading — so it is not a route and adds no links for a crawler to follow. A video counts as anime when its category or one of its tags says so (`anime`, `hot-anime`, `#anime`), and as premium when the record carries a premium flag (`premium: true`, `isPremium: true`, `premium` in `metadata`), a category, a tag or a badge that says it — the same way the API already reports `exclusive`. "Desi" is deliberately *everything that is neither anime nor premium*, because the catalogue also carries uploads from other countries (a country name would be wrong for them) and a premium title has its own row. "Sponsored" switches the grid to the partner cards alone, with no catalogue rows mixed in. An empty filter says so instead of showing a blank page, and the bar scrolls sideways on a narrow phone rather than widening the page.

**All Videos is four rows, in this order: Desi, Anime, Sponsored, Premium.** A row with nothing in it is not drawn, and no video is drawn twice — a premium upload appears in the Premium row only. The four rows replace the old mix of partner cards inside the catalogue grid, so a visitor always knows which row a card came from; Trending, New and Exclusive keep the interleaved "four of ours, then one of theirs" rhythm.

The hero is a poster on a phone and a poster-plus-copy block on a desktop. On a screen narrower than 768px (or a coarse-pointer tablet) it shows only the artwork: no title, creator, meta line, WATCH NOW or arrows. The carousel moves with a finger — a mostly-horizontal swipe — or with the dots that sit on the poster. On a desktop the copy comes back and the two arrows float vertically centred on the banner itself, one just inside the left edge and one just inside the right edge, with the copy indented clear of them.

The actual pages have stable URLs: `/`, `/trending`, `/new`, `/exclusive`, `/categories`, `/search?q=...`, `/login`, `/profile`, `/referral`, `/dashboard`, and `/watch/<id>`. Navigation links, direct entry, refresh, and browser back/forward restore the corresponding page. Account pages still require the appropriate sign-in/profile state. The 18+ confirmation belongs to the front door: opening `/` asks once per tab, and every other address — a shared `/watch/<id>` link, a search result, an account page — opens the page it names without asking again. Search terms are included in the URL, so they may be saved in browser history or server logs, or shared when a search link is copied; do not put secrets in search queries.

Opening a video updates the address to `/watch/<id>`. Shared links do not contain a backend address. A recipient discovers their own backend and opens that ID there. The backends therefore need to serve the same video IDs for links to work across visitors. A missing video or failed request shows a generic message without a server address.

## Streaming and caching

After age confirmation, opening a video mounts one native player with the video's stable, pinned backend URL and poster. The browser handles HTTP ranges and buffering directly: there is no parallel JavaScript downloader, Blob URL, cache-busting query, or media preload for catalog cards. Clicking a card's play button or “Watch Now” attempts to start playback immediately; if the browser blocks it, the regular play button remains available. Shared links do not autoplay after the age gate. The player suggests `preload="auto"` for the selected video and `metadata` when the browser reports data saver or a 2G connection. These are hints, not transfer limits: browsers may ignore them, playback requests buffering regardless of the hint, and `auto` can download the whole selected video. The player indicates buffering, allows retry on errors, and supports click and keyboard seeking. The backend currently offers one source, so the UI does not pretend to switch quality.

**A premium click never shows a player while the account is being checked.** The account check (`/api/auth/verify`, then `/api/auth/me`) is asynchronous, so a premium video is gated from the first frame: until it answers, the overlay shows the sign-in notice with a disabled “Checking your account…” button, no play button, no transport UI and no media request. If the answer is a member, the gate lifts on its own, the notice is replaced by the real player (the trailer that was already issued), and a play request made during the check starts then; a browser that wants a fresh gesture still finds the play button. If the answer is a guest, the same notice stays with an active **Sign in to watch** button, so no visitor is ever bounced to the sign-in page by a check that had not finished.

**The 18+ gate says what it means.** The front-door card keeps three plain blocks: the warning, the sentence describing the ENTER button, and the small print. The terms line carries its own top spacing (and is wired to the button with `aria-describedby`), so it reads as the condition of **I AM 18+ – ENTER** instead of trailing the warning box; the card's bottom padding is larger than its top so the last line is not pressed against the gold border; and the small print uses `gray-400` rather than `gray-700`, because `gray-700` measured 1.92:1 on the card's dark surface — under half of the 4.5:1 AA floor. The privacy line is a statement, not a control: it stays plain text instead of looking like a link that goes nowhere. `test/mobile-layout.test.mjs` asserts the grouping gaps, the bottom breathing room, the contrast ratio and the absence of a dead link.

**A guest is asked to sign in first.** A premium video is for members, so a visitor who is not signed in is not shown a player at all: the overlay says “Sign in first to watch this premium video”, explains that premium is for signed-in members, and offers a **Sign in to watch** button that closes the player and opens `/login` — the page that carries the Google button. Nothing is requested behind that gate (no trailer, no stream, no ad), and the video's own address stays in history so browser back returns to it. The backend remains the authority on who may watch; this only stops a signed-out visitor from being offered a premium player. A signed-in member sees the trailer/full-video behaviour above.

**An expired link renews itself.** Stream and trailer links carry a short-lived token, so a player left open past it used to end in “Reload the page”. Instead, a media error on a tokenised link asks the backend for this video again (`/api/videos/<id>`, the same detail route as a normal click) and installs whatever link that answer carries: the token is replaced in place, the position is kept, and playback continues without the visitor doing anything. The same refresh runs once when a member's account check finishes after the player already opened with the locked shape, so a confirmed member is moved from the trailer to the full video instead of staying on the trailer forever. A guest's answer never contains a stream link, so the refresh can only ever return the trailer — the backend stays the only authority on what may be played. Only when a second refresh in a row also fails is a message shown, with a **Try again** button that asks for a new link rather than reloading the dead one.

**A premium title never gets a pre-roll.** The ad overlay belongs to the catalogue player, and a premium video is not an ad slot: for a title the backend marks `premium`, or answers `locked` for (both are kept as `premium` on the player's video), the ad tag is never requested and playback starts on the click. A locked title plays its trailer at once and carries two notes — “Trailer · full video premium members ke liye” and “Premium video · abhi sirf trailer. Sign in karke premium activate karo, phir full video chalegi.” A locked title with no trailer loads nothing at all and shows “Premium video · sirf premium members ke liye”, “Sign in karke premium activate karo — uske baad yahi video full chalegi.” and the fact that no trailer is available either. A premium member's full video plays with no ad in front of it and no trailer note.

**A premium video plays only the link its premium window allows.** The catalogue reports `premium`, `locked`, `hasTrailer` and a `trailerUrl` for premium titles, and the app decides nothing itself: the metadata is only used to pick *which* of the backend's links to load. With an active window the player uses the tokenised `streamUrl` exactly as issued (the token carries the premium-until time, so it is never rebuilt, cached or shared); when the video is `locked` it plays `trailerUrl` (which needs no window) and labels itself “Trailer · full video premium members ke liye”; when a locked video has neither a trailer nor a stream it draws a panel instead of loading media. A failed trailer shows “This trailer link expired. Reload the page to watch it again.”, and the player never falls back from a trailer to the stream — the server's answer (403 `Premium required`, 403 `Link expired — reload the page`, 404 `No trailer for this video`) stays the only authority. `src/services/api.ts` accepts a media link only when it is `https:`, same origin, exactly `/api/videos/<id>/stream` with at most the `t` (and, for trailers, `kind=trailer`) parameters, so a catalogue cannot point the player at a third-party file.

**The referral window is redeemed on the dashboard.** The Premium panel reads `GET /api/premium/status` and `/api/premium/history` with the account's bearer token and offers only the redemptions the server says are available (one referral = 2.5h, two = 5h, four = 10h, priced from `referrals.secondsEach`). `POST /api/premium/redeem {count}` is sent with the same token; the panel shows the returned window and then re-reads the catalogue, because the stream links already in the page were issued for the window that just changed. A refusal (no referrals, too few, unavailable) is shown in the app's own words and never retried in a loop.

**A tap on the picture never pauses.** The video surface toggles the controls: the first click hides the timeline, the next brings it back, and playback keeps running either way. Pausing is the pause button's job — the bottom control, which is also the only thing that resumes a paused video besides the large centre button. While playing, the controls fade after three seconds of no pointer movement; while paused they stay until the visitor clicks the picture. The pointer movement that precedes a click is ignored for a quarter of a second, so a click does not immediately re-show what it just hid.

**A transient failure is retried before the visitor is told.** The first catalogue page, a shared `/watch/<id>` link and a search are wrapped in `src/services/retry.mjs`: two quiet attempts for the catalogue (three after returning from a PHP host's check page), one for a shared link and a search. "Content Unavailable", "This video is currently unavailable" and "Search failed" therefore only appear after those attempts, and the "Retry Connection" button still gives the PHP session its budget back.

**A cut media request repairs itself.** A media element that fires `error` never plays again until it is asked to reload, and the pre-roll makes that likely: while the ad's own `<video>` uses the network, browsers throttle or abort the content's request (mobile is strictest), so the content element reached the error state before the visitor pressed play — the old code answered with “This video could not be played. Please try again.”, a button for something the player can do itself. `src/services/playback-recovery.mjs` decides when one silent `load()` is worth it: an aborted or network failure gets two attempts, an unreadable source (a host's check page, a 503 without a media type) one, and a blocked `play()` none, because autoplay policy needs a gesture and reloading would discard the buffer. While the ad is on screen nothing is shown at all; the reload happens the moment the ad ends, and “Try again” is painted only after the silent attempts are spent. The element's `crossOrigin` is also fixed for the player's lifetime, since changing it makes the browser discard a load in progress.

**A CDN file and a byte stream are both playable.** Newer uploads can live on the server's CDN host while the older ones are streamed byte-for-byte by the backend, so `src/services/media-source.mjs` decides what goes into `<video src>`. An absolute `cdnUrl` in the catalog is used as the source with the backend's `/api/videos/<id>/stream` kept as the fallback; a media-looking `streamUrl` or `bestfile.download_link` (`…/clip.mp4`, a `cdn.*` host) is treated the same way; everything else — the backend's own stream route, a third-party tracker, an `http:` URL, a download *page* such as `https://bestfile.io/<id>/file` — is skipped in favour of the byte stream, because a page answers with HTML and a media element can only fail on it. If a CDN file fails anyway (expired, hotlink-blocked, deleted), the player switches to the byte stream once, keeps the playback position and continues without another click. A CDN source is also requested without `crossOrigin`, since those hosts rarely send CORS headers and `anonymous` would turn that into a hard error.

A backend response of `Cache-Control: public, max-age=3600` permits browser caching where the browser supports it; it does not ensure a cache hit, a shared cache, or a speed increase. Keep video IDs immutable for that period (or deploy a versioned URL and purge changed content), and return a strong `ETag` for safe range validation and combination. The inspected stream route does not explicitly set one. Vercel's [CDN cache criteria](https://vercel.com/docs/caching/cdn-cache#cacheable-response-criteria) exclude requests containing `Range` and `206` responses; dynamic CDN caching also needs an appropriate shared-cache policy. Do not assume native range requests are served from Vercel's CDN just because `max-age` is present. The browser tests use a cacheable local fixture with a strong ETag; this does not verify either deployed backend.

**Backend streaming checks required:** the inspected backend `main` revision (`17908bae2a17124c838b732b2d1ad28812184b37`) has the same stream source as `5e499b39408397c637b9153b1270f307d1575733`. In local mocks of the extracted `GetFile` path, 17 aligned chunks remained in order with at most eight concurrent calls; unaligned, multi-batch and 13-byte EOF ranges returned exact bytes, using a 512 KiB request limit even at EOF. The extracted route returned `416` with `Content-Range: bytes */<size>` for the tested reversed and unsatisfiable ranges.

Short or empty non-final `GetFile` responses are still silently accepted. A mock returning 42 fewer bytes from a middle part produced the advertised response length but the wrong bytes, because later bytes filled the gap. Validate each returned chunk against the file size and requested interval; retry a missing part at its original offset or abort rather than skipping it. A genuinely short final part is valid when its length matches the remaining file bytes.

The separate fast-start path needs attention. Its `findMoovAtom` still sends a shortened final `GetFile` limit, and `readFileRange(video, 0, 31)` requests an invalid 32-byte limit under Telegram's non-precise rules; strict local mocks rejected these calls. Its scan can start inside `mdat` and miss a tail `moov`. With permissive local mocks and the actual MP4 test fixture, the route misidentified an existing beginning `moov` as a tail atom and returned HTTP 200 with only 2,732 bytes from an 832,606-byte video, omitting `mdat`. Do not return only `ftyp` and `moov` as a complete video; serve the original representation with correct ranges, or fully remux to a consistent fast-start file before upload, adjusting offsets and supporting ranges against that complete representation.

The backend waits for each batch before yielding and does not start the next until that batch is yielded; this is not overlapping prefetch. Its small-file path downloads files under 50 MiB in full before yielding the first bytes. The stream code sets `Vary: Origin, Range`, but `vercel.json` separately sets `Vary: Origin` and specifies `Access-Control-Allow-Origin` twice on the same route; verify final deployed headers and CORS. Actual Telegram behavior, live streaming and first-frame speed remain unverified.

Before deploying, test representative small and large videos on each actual backend. Compare response bodies byte-for-byte for one- and multi-batch ranges, unaligned starts/ends, partial final parts, suffix ranges and ends beyond EOF. Check cancellation/backpressure, CORS, errors, first-frame time and repeat-view caching in target browsers; frontend mocks and backend settings do not verify production behavior.

## Catalog views

The first catalog page is shown immediately; subsequent pages are collected from the same selected backend in the background, with overlapping IDs and repeated terminal cursors handled safely. Trending ranks the collected catalog by numeric view count. New shows all uploads from the visitor's local calendar day, or yesterday's uploads only when today has none; older, future, and undated items are not treated as new. Home includes both normal and exclusive videos. Exclusive uses a public `exclusive: true` flag (also accepting an exact `Exclusive` category or tag when no explicit flag is supplied); an explicit `exclusive: false` takes precedence over labels. The backend must include this metadata in its public response; the frontend cannot infer flags that were not returned. Categories currently shows only a Coming Soon message. Home shows the catalogue and nothing else: the Trending, New and Exclusive rows live only in their own tabs, so nothing is repeated above the grid. The browse tabs are part of the bar on every screen size — on a phone the row scrolls sideways and the active tab is centred after each navigation, so Home, Trending and New are never pushed into the hamburger menu (which now holds only Notifications and Account).

The current backend offers date-ordered pages rather than server-side trending or exclusive queries. To avoid presenting an incomplete ranking as complete, the UI reports a retryable incomplete-catalog state on failed, ambiguous, or excessive pagination. Page requests are capped at 50 items and the scan at 120 pages; large catalogs are better served by dedicated server-side sort/filter endpoints. Entering a feed after the catalog has been idle for a minute refreshes the metadata. Cards render incrementally as the visitor scrolls.

## PHP host behind a free-host check (direct cookies)

Some free PHP hosts (InfinityFree and its siblings) answer every request with an HTML page that runs a scripted check and stores a `__test` cookie. The site still talks to that host **directly** — no proxy, no server in between. The host's own cookie is the only credential, and the host's own unlock page is the only thing that can hand it out.

**One flag decides the transport.** Discovery answers `{ "ok": true, "data": { "server": "…", "php": true|false } }`.

- `php: true` — the host hides its API behind a cookie check, so: `credentials: "include"` on every API and media request, no `crossorigin` attribute on that host's media (a CORS request would drop the cookie), a `text/html` answer (or a request the browser could not read) treated as the check instead of an error, and preflight-free account calls (see below).
- `php: false` — or a response without the field — the ordinary behaviour, untouched: a credential-free direct call (`credentials: "omit"`), `Authorization: Bearer` with JSON bodies, `crossorigin="anonymous"` media, and no redirect at all.

`src/services/php-session.mjs` remembers the flag for the tab, so media and account calls follow the same rule as the catalogue. `src/services/media-credentials.mjs` decides the media attribute from that same origin.

**The cookie flow.** On a `php: true` backend a direct call that comes back as HTML (or that the browser refuses to read, which looks identical) is not shown as an error. The visitor sees a short splash and the browser navigates once to `<server>/__unlock?back=<current page>`; that page runs the host's check, stores its cookie and returns the visitor to where they were with `?__unlocked=1`. On the way back `src/main.tsx` cleans the address bar. The first JSON answer that actually arrives proves the cookie works, and the window stays quiet for 5.5 hours (`UNLOCK_FRESH_MS`). A window that never confirms gets at most three unlocks (`UNLOCK_MAX_TRIES`) with a four-second gap (`UNLOCK_MIN_GAP_MS`), then the ordinary "Content Unavailable" screen — whose **Retry Connection** button gives the budget back instead of leaving the page dead. `PHP_ORIGIN_OVERRIDE` in `src/config/php-backend.mjs` is empty in normal use; setting it pins one host for testing.

**What the PHP side must provide** (only these three things; nothing on the frontend can replace them). Copy-paste code for all three, including the `.htaccess` rewrite, is in [`docs/php-unlock-backend.md`](docs/php-unlock-backend.md):

1. **`/__unlock?back=…`** — a page that runs the host's check and then redirects back to `back` with `?__unlocked=1` appended.
2. **`__test` re-issued as `SameSite=None; Secure`** on that page. A cookie left at the host's default `SameSite=Lax` is never sent on a cross-site request, so the API keeps answering with the check page.
3. **CORS on every API answer**, including the ones served with the cookie: `Access-Control-Allow-Origin: https://intimora.net` (the exact site origin, not `*`), `Access-Control-Allow-Credentials: true`, and `Vary: Origin`. A cross-site response without these cannot be read by the browser at all, and no frontend change can work around it.

**Preflight-free account calls.** A CORS preflight (`OPTIONS`) is sent without cookies — the Fetch spec forbids credentials there — so on a host that gates everything behind a cookie-based check, every request needing one can never succeed: the preflight itself gets the HTML check, which carries no `Access-Control-*` headers, and the browser reports a CORS failure. A custom `Authorization` header and a `application/json` body both trigger exactly that.

Account calls are therefore "simple requests": the Firebase token travels in the body, the content type is `text/plain`, every account route is called with `POST` (a `GET` cannot carry a body) and `credentials: "include"` lets the host's cookie travel. `src/services/auth-request.mjs` sends `{ token, … }` for `/api/auth/verify`, `/api/auth/profile`, `/api/auth/me`, `/api/user/referrals` and the video like/save actions, and treats a `text/html` answer — or a blocked request — as the host's check, which is the one case that asks for the unlock navigation. The backend must read the token from `php://input` (accepting a `text/plain` body) as well as from an `Authorization` header. Because the cookie is `SameSite=None`, a state-changing route should also require the expected `Origin`.

**When it still fails, the reason is on screen.** Every direct call reports how it ended — the host's check page (`check-page`), a request the browser refused to hand over (`blocked`, the CORS case), the server's own error status (`status`), or a JSON shape this client cannot read (`shape`) — and `src/services/api.ts` turns that into the sentence on the "Content Unavailable" screen instead of a generic message. On the way back from `/__unlock` the first catalogue request is retried twice (1.5 s apart) before any error is painted, because the browser can still be settling the cookie. `__intimoraDiag()` in the browser console prints the last 40 events (target, `php` flag, each request's path and outcome, each unlock) as a table; it never records tokens, cookies, headers or bodies. `node --test test/php-diagnostics.test.mjs` covers all of it.

`node --test test/php-unlock.test.mjs test/php-challenge.test.mjs` pins this behaviour: both transports end to end, a discovery answer without the flag, no redirect for an ordinary backend, the bounded retry budget, the cookie proof on the first JSON answer, the media attribute following the flag, and the plain-JS AES of the host's check matching `node:crypto` byte for byte. `scripts/php-challenge.mjs` is that check implemented for a terminal, `scripts/php-api-check.mjs` walks every endpoint of a PHP host with it, and `scripts/php-api-check.mjs https://intimora-api2.site.je` is the quickest way to see whether a host answers JSON at all. Neither script is used by the site.

## Security and CORS

Direct access means the discovery response, selected backend URL, API responses and network requests are visible in browser developer tools. **Do not send secrets, tokens, signed URLs, private error details, or other confidential data in public Worker/backend responses or public build variables.** The frontend can filter displayed fields, but it cannot hide a response that the browser has already received. Secrets belong in backend-only environment variables and must not be committed. Public URLs and CORS are not authentication: protect sensitive backend routes with proper authentication, authorization and rate limits. The age gate is not age or identity verification.

Every selectable backend and the Worker must allow the deployed site's exact origin in CORS (or `*` for public, credential-free access). Allow `GET`, `POST`, `HEAD` and `OPTIONS`; permit `Content-Type`, `Authorization`, and `Range` on preflight requests. Thumbnail and stream responses must also allow the origin, including byte-range responses. A stream should support `Range`, `206 Partial Content`, `Content-Range` and `Accept-Ranges`. Discovery and an ordinary backend fetch omit cookies and referrers, and neither follows API redirects. The one exception is a backend the load balancer flags with `php: true`: that host is called directly with its own session cookie (`credentials: "include"`), which is why it needs the credential-aware CORS headers described above. The separate Google popup uses the visitor's normal Google sign-in session. It accepts only public HTTPS discovery/backend URLs without credentials or query strings and uses the standard video media routes instead of arbitrary third-party media URLs.

The static site's CSP permits HTTPS connections, images and media because discovery can select different public hosts, while restricting scripts to the site and Google's Firebase sign-in script. It also permits the Firebase auth domain and Google Accounts as frames for the popup flow, plus `https://hdzog.com` for the sponsored TubeCorporate campaign iframe. If you change the campaign host, update `PARTNER_EMBED_HOSTS`, the CSP in `server/security.mjs` and `render.yaml`, and the tests together. If all legitimate backend and Worker hosts are known and stable, narrow those HTTPS sources in Render's Content Security Policy. Other security headers and a `no-referrer` policy are included in the Blueprint. CORS is enforced by browsers, not by curl or other servers.

## Google accounts, libraries and referrals

The account circle opens Google popup sign-in (with account selection). After the age gate, Firebase restores the existing session, `/api/auth/verify` checks whether the Firebase UID has an account, and `/api/auth/me` supplies its profile and liked/saved video IDs. New users enter a name, a username, and an optional referral code; both Skip and an empty Finish submit without a referral. Registration and confirmation use the same trusted backend. A temporarily missing record is checked again briefly, and an unconfirmed write shows an error instead of silently looping or pretending the account was saved. Guests who try to like or save are sent to sign-in rather than making local-only changes. Like/save buttons react immediately but display a pending state until confirmed; a failed or uncertain request restores the previous confirmed state and asks the user to refresh/check before retrying. The dashboard displays the stored referral code and matches the user's IDs against the public catalog; it does **not** load video details just to build a library, because the backend counts those requests as views. Videos missing from a partial/outdated catalog are reported as unavailable.

**Public likes and action speed need backend work:** the inspected backend updates the user's like list but not the public video aggregate. Its new per-instance user cache can avoid warm Telegram scans, but actions still wait for a Telegram edit and Firebase lookup; local mocks also exposed failed-write and cross-instance cache consistency risks. The frontend does not manufacture a count or make that server write faster. It can consume a versioned count from an upgraded like response and, once the backend contract is deployed on all hosts, poll visible public counts approximately every five seconds. Polling is **off by default**; only then set `INTIMORA_PUBLIC_LIVE_LIKES=1` at frontend build time. Exact API responses, shared atomic storage, migration, authentication, compatibility and measurement instructions are in [the backend handoff](docs/live-likes-backend.md). Live production performance and cross-user updates remain unverified until the backend and frontend are deployed and tested.

**Backend account persistence:** the previously inspected backend revision `5082669c2b02f942326d5831cf535ee3cc5110f9` passed an object to a Telegram wrapper that expected text. A local test using the backend functions and Teleproto stored `[object Object]` instead of user JSON, so a successful create could not be found by UID. Backend `main` revision `1d538bddaac49dd6d2ece29f66ef24c1fa81e510` changes user and referral writes to pass JSON strings and disables Markdown parsing for those sends and edits. With the current backend source and mocked Telegram storage, Skip, blank Finish, valid referral links and subsequent user lookup passed locally. GitHub reports successful Vercel deployment statuses, but live account persistence and both hosts remain unverified. Ensure both backends share the intended account storage, then test registration, referral links, reload/sign-in, and saved/liked actions with a real account. Existing failed registrations may need to complete the profile again.

Firebase's web app configuration in `src/services/firebase-config.ts` contains public client identifiers, not a service-account credential. Restrict the Firebase API key to the required APIs, review quota limits, and keep actual credentials on the backend. In Firebase Authentication, enable the Google provider and authorize the exact deployed hostname and any development origin; configure the Google consent screen/branding as needed. Browser tests use a mock identity provider; verify the real popup, Google project settings, production CORS (including `Authorization` preflights), token verification, and persistent accounts in a deployed browser. Popup sign-in is used deliberately: redirect sign-in on a different hosting domain needs additional Firebase auth-domain configuration. Do not paste Firebase tokens or service-account credentials into logs or chat.

The Worker still selects the visitor's backend. Bearer tokens are sent only to the **exact** trusted auth origins `https://api-intimora.vercel.app` and `https://intimora-api1.vercel.app`, even if discovery returns a different host. Authenticated video actions remain pinned to the trusted backend that supplied that video. If the actual backend fleet changes, explicitly update the public build-time `INTIMORA_PUBLIC_AUTH_BACKENDS` comma-separated origin allowlist after reviewing each new host; the change is not automatic and the value must not contain secrets. Browser requests omit cookies, disallow redirects, and show generic service errors.

### Direct links without a host rewrite

A static host serves an existing file before it evaluates any rewrite rule, so the build publishes a real HTML file for every page. `/trending`, `/new`, `/exclusive`, `/categories`, `/search`, `/login`, `/profile`, `/referral` and `/dashboard` are written as both `<page>.html` and `<page>/index.html`; every `/watch/<id>` listed in the published sitemap becomes `watch/<id>.html` and `watch/<id>/index.html`; and `404.html` holds the same app shell. Rebuild the site (the daily sitemap workflow already does) or add the wildcard rewrite to publish shells for new videos with a `200` status. Unknown paths also receive `404.html`, so they load the app instead of a bare host error page; this is a soft 404.

## Ranking for the brand name ("Intimora")

Search rankings are decided by Google, not by the repository, so nobody can promise first place for a query. What the build now does is remove every technical reason for a page to be ignored:

- **Head of the home page.** `<title>Intimora | 18+ Adult Video Streaming</title>`, its own description, `og:`/`twitter:` cards, one `<link rel="canonical" href="https://intimora.net/">`, `og:url`, `og:image` (`/logo.png`) and `<meta name="rating" content="adult">`.
- **Structured data.** The `WebSite` node carries `name`, `alternateName` (`Intimora.net`, `Intimora adult videos`), `inLanguage`, `publisher` (`Organization` + logo) and a `SearchAction` for `https://intimora.net/search?q={search_term_string}` — the two things Google uses for the site name above a result and the sitelinks searchbox.
- **A real heading.** The home page had no `h1` (the hero shows a video title); it now starts with a visually hidden `Intimora — free 18+ video streaming`.
- **One head per page.** Every generated shell (`/trending`, `/new`, `/exclusive`, `/categories`, `/search`, `/login`, `/profile`, `/referral`, `/dashboard`, `/watch/<id>`) gets its own title, description, canonical and `og:url`; the watch pages also carry a `WebPage` node with `contentRating: 18+`. `404.html` is `noindex, follow` and has no canonical. Catalogue titles are escaped and cut at 70 characters before they reach the HTML.
- **Sitemap and robots.** `sitemap.xml` lists the site pages and up to 500 `/watch/<id>` URLs; `robots.txt` allows everything and points at it.

**Verification tag (one step for you).** In Search Console add a property for `https://intimora.net/`, choose **HTML tag**, copy only the `content` value, and set it as `INTIMORA_PUBLIC_GOOGLE_SITE_VERIFICATION` on the Render service. The build injects `<meta name="google-site-verification" …>` only when the value looks like a token (`[A-Za-z0-9_-]{20,80}`), so an empty variable changes nothing.

**Realistic expectations.** A brand-new domain needs (1) Google to crawl it, days to weeks after the sitemap is submitted, (2) SafeSearch to be off in the searcher's browser — adult sites are filtered by default, (3) some backlinks from pages that mention "Intimora", which no build step can create, and (4) the 18+ gate sits on `/` only, so Google and shared links reach the catalogue pages directly and a visitor arriving from search never meets a gate. Search Console → **URL Inspection** shows exactly what Google saw; if it reports the age gate, that is the gate doing its job, not a bug.

## Sitemap and Google Search Console

The site publishes one XML sitemap at `https://intimora.net/sitemap.xml` and advertises it in `/robots.txt`. Every sitemap lists the site's own pages first — `/`, `/trending`, `/new`, `/exclusive` and `/categories` — followed by the public video pages (`/watch/<id>`), so a crawler always finds the real Intimora pages even when the catalog scan fails. The checked-in fallback is a snapshot of those pages and the public video links available when this change was prepared. During a production build, Vite reads the **public** discovery endpoint and its selected backend's catalog, replacing that snapshot with valid `/watch/<id>` URLs for normal and exclusive videos. It follows overlapping pages, deduplicates IDs, and caps the scan at 120 pages of 50 with a 60-second overall deadline. The sitemap contains site URLs only, not backend addresses, titles, or private data. If discovery, a page, or the scan fails, the build logs a generic warning and retains the checked-in snapshot, which may be out of date; check the published XML and build log after deployment. A repeated full page is treated as incomplete because the backend's cursor can conceal items with the same timestamp.

Render is a Static Site: the sitemap is a **build-time snapshot**, not a live endpoint. New uploads and removals appear at the next successful deploy/rebuild, not immediately. To update it manually, redeploy the existing static site. An optional workflow at `.github/workflows/refresh-sitemap.yml` can request a rebuild daily at 02:17 UTC (GitHub schedules may be delayed):

1. In the existing Render Static Site's Settings, find its deploy hook. Treat this URL as a secret.
2. In the GitHub repository's Settings → Secrets and variables → Actions, add it as the repository secret `INTIMORA_SITEMAP_DEPLOY_HOOK_URL`. **Never commit it or paste it into chat.**
3. Enable GitHub Actions on the default `master` branch. The workflow also supports a manual run. Without the secret it safely skips; with it, each run requests a Render deploy and consumes build minutes.

After the changed branch is merged and deployed, open `/sitemap.xml` and `/robots.txt` to confirm they return the expected files. In the verified Google Search Console property for `https://intimora.net/`, open **Indexing → Sitemaps**, enter `sitemap.xml`, and select **Submit**. A sitemap is a discovery hint, not an indexing or ranking guarantee. The 18+ gate guards `/` only: search-result and shared links open the page they name, so Google can reach `/watch/<id>` and the browse pages without a gate. Use URL Inspection and Google's [video SEO guidance](https://developers.google.com/search/docs/appearance/video) to diagnose this without weakening the gate.

The site counts visits with **Cloudflare Web Analytics**, embedded as a single module tag in `index.html` with the site token. ## Anime titles (live API)

Anime cards come from our own anime API, **`https://pacahub-34nd.onrender.com`** (a deployment of the PacaHub service). Nothing about that content is baked or scraped into this repository any more: the page asks the API when it opens and draws whatever the service sends.

- **Rows:** `GET /api/hen/city/recent` and `GET /api/hen/city/popular/1`, asked for **in that order** — Recent first, then Popular, exactly as the anime page shows them. `…/popular/:page` and `…/top/:page` exist on the service; `…/info/:id` and `…/watch/:id` are available for a single title. The repository keeps no copy of any row, so the page is always as fresh as the service.
- **Card facts:** a list row carries an id, a title, a poster and a duration, so that is all a card shows. No author, rating or tags are invented, and no per-title request is made. The id is taken from the end of the source slug (`…/video/<slug>-<id>.html`) and validated; a poster must be a plain `https` image URL. A row that fails is dropped, not faked.
- **The id is the whole slug.** The list gives `id` as a full slug (`…-girls-6-1JdXN6yeMdN`) and the watch route needs it whole: asking with only the trailing code (`1JdXN6yeMdN`) is exactly what the service answers with `{"status":"error","message":"Failed to scrape HentaiCity watch: Request failed with status code 404"}`. A card therefore keeps `id` (the slug, used for the watch route) and `code` (the tail, used only for the embed URL and the poster's video id), and duplicate titles are matched on `code`.
- **Click:** the card asks the service's own watch route, `GET /api/hen/city/watch/:id`, and plays the link it answers with — exactly as received, in our overlay. **That answer is normally an HLS playlist** (`data.source[].src`, `formate: "hls"`, a `…/master.m3u8` URL), not a file, and a playlist cannot go into a `<video src>`; Chromium answers it with "no playable file". So a playlist is handed to `hls.js`, which reads the playlist and its segments from the source host directly and feeds the element through MediaSource; where the browser has no MediaSource (Safari on iOS) the browser's own HLS reader plays the same URL. Either way nothing is proxied, no URL or segment is rebuilt, and an iframe is not used. `src/services/anime-api.mjs` accepts only a plain `https` URL that ends in a media file **or `.m3u8`** (a page, a download host, `http:` or a script URL is refused), and picks the first playlist it finds. Before a playlist is handed to the player it is fetched once (`hlsPlayable`): a manifest whose host refuses this page (403 or a CORS rejection — the source checks referrer/origin on its segments) is **not** played, and the overlay says “Is title ka video source hamari site ko nahi de raha. Baad me try karo.” instead of leaving a stuck spinner. That limit is the source's, not the app's; the overlay records what it played in `data-anime-src` and how it played it in `data-anime-via` (`hls` or `src`). When there is no link at all the overlay says so with a retry instead of hanging. The ad overlay belongs to our own catalogue player, so an anime click never gets a pre-roll.
- **All Videos:** the anime cards sit in the **Anime** row of All Videos (right after **Desi**), and under the **Anime** chip as the API's own two rows.
- **Search:** matches are computed on the cards the page already loaded (the source's `/search/` is disallowed to crawlers), so no query leaves our origin and no search request is made to the API.
- **No like/save on anime cards:** those actions need a video id in our own backend, and an external title has none. The cards therefore show no like/save button instead of a button that always fails.
- **CSP:** `media-src https:` and `connect-src https:` already allow the source's playlist and segment hosts, `frame-src` lists `https://www.hentaicity.com` in both `server/security.mjs` and `render.yaml`, and `img-src https:` covers their poster CDN.

## Sponsored partner videos (TubeCorporate)

Partner videos are **part of the catalogue layout**: every fourth card is followed by one sponsored card ("four of ours, then one of theirs") on Home, Trending, New and Exclusive. Each sponsored card uses the site's own card markup, outline, hover and typography, and the badge slot that shows `EXCLUSIVE` on our videos shows `SPONSORED` on theirs. Titles and posters come from the partner page itself (`og:title`, `og:image`), so a sponsored card looks like one of our own.

Clicking a sponsored card opens **our player** — the same full-screen overlay, frame and close control as any other video — with the partner's player inside the frame. No pre-roll, no like/save and no related-video logic runs for sponsored content, and nothing appears in search results, on account pages, before the age gate, or on the watch page.

The value lives in exactly one place: `PARTNER_EMBED_URL` in `src/config/partner-embed.ts`. Two shapes are accepted:

1. **A single video embed page**, e.g. `https://desi-porntube.com/embed/762647/?source=1849513610` — rendered as one iframe at the bottom of browse pages.
2. **A campaign CSV feed**, i.e. the "feeds" link from the TubeCorporate dashboard, e.g. `https://desiporn.tube/admin/feeds/embed/?categories=…&source=1849513610&feed_format=csv&tag=girls&csv_separator=%7C&csv_columns=embed`. Each row is a ready-made `<iframe src="…">` snippet, **not** a web page: framing the feed URL itself would only show raw CSV. The build reads it once, extracts the `src` of every iframe, re-validates each URL, drops duplicates and caps the list at 60; the first 24 are then read individually to pick up their title and poster, and the result is published as same-origin `/partner-feed.json` (`version: 2`, one object per video).

**Titles and posters.** A card's preview is resolved from four sources, in this order, and the first one that answers wins:

1. **The feed row itself.** If the pasted feed URL asks for more columns (e.g. `csv_columns=embed,title,screenshot`), each row carries the video's name and poster next to the iframe. Those values are used directly and no page is read at all.
2. **The embed page**, fetched the way a browser fetches it (`Accept`/`Accept-Language` headers, a desktop user agent), because many partners answer a bare bot agent with a challenge page instead of their Open Graph tags. If that page yields nothing, it is retried once with a phone user agent.
3. **The partner's own video page** (`/video/<id>/`, then `/videos/<id>/` on older templates), which carries the same tags and is far less likely to be bot-protected.
4. **The predictable screenshot paths** (`/contents/videos_screenshots/<bucket>/<id>/320x180/1.jpg` and neighbours), each confirmed with a `HEAD` request that must answer `200` with an `image/*` type — an HTML error page is never used as a poster.

The poster is taken from `og:image`, `og:image:url`, `og:image:secure_url`, `twitter:image`, `<link rel="image_src">`, a `<video poster>` or a JSON-LD `thumbnailUrl`; protocol-relative and root-relative paths are resolved against the page that produced them, and a plain-`http` poster is upgraded to `https` instead of being thrown away. Challenge-page titles ("Just a moment…", "Content not found", "403 Forbidden") are discarded so they never appear on a card, and a trailing site name such as `| DesiPorn` is trimmed. The build reads exactly as many embed pages as the grid can display (24), so a card that is shown is never the one without a preview, and a page that fails still yields a card. When nothing resolves, or the partner CDN refuses the poster (hotlink protection, expired link), the card shows a neutral "partner video" tile with the play mark instead of an empty black rectangle; the same tile replaces a poster whose image load fails in the browser.

**Build log.** Every build prints one line, e.g. `Partner previews: 21/24 pages resolved (24 with a title).`, so a deployment can be checked without inspecting the site: `0/24` means the partner host is refusing the build server (a network or bot-protection problem on their side), while a lower poster count than title count means titles work and only the images were refused.

**Nothing third-party is contacted before the age gate.** The client reads only `/partner-feed.json` from its own origin — once, after age confirmation — so the feed host needs no CORS headers. If the feed cannot be read (host down, empty, no usable rows, timeout), the build logs `Sponsored feed could not be read` and the sponsored cards are simply absent; the site still ships.

`src/services/partner-embed.mjs` validates both shapes before they are used: HTTPS only, no credentials or fragment, an `hdzog.com`, `tubecorporate.com` or `desi-porntube.com` host for embeds, a `desiporn.tube` / `desi-porn.tube` host for feeds, an `/embed/<id>` path for feed rows, and a numeric `source` parameter (appended automatically when the pasted URL omits it). An unknown host, a non-HTTPS URL or an unsafe query fails the build, so a mistyped value cannot ship. `src/services/partner-cards.mjs` validates the published cards again, and `npm test` covers both shapes, the mixing rule and the player.

**Where to change it:** edit the single `PARTNER_EMBED_URL` line in `src/config/partner-embed.ts`, save and commit; the build picks the shape automatically. The public build variable `INTIMORA_PUBLIC_PARTNER_EMBED_URL` overrides the file (it is bundled into browser code, so never put a secret there), `INTIMORA_PARTNER_FEED_TIMEOUT_MS` (500–60000, default 10000) bounds the build-time feed request, and `INTIMORA_PARTNER_FEED_OFFLINE=1` skips the fetch entirely — the test suite uses it so tests never contact the campaign host. The CSP allows frames from `hdzog.com` and `desi-porntube.com` only.

Third-party content stays outside this site's control: ad blockers can hide the cards, the campaign's own availability, cookies, creative quality and anything its player overlays (including its own branding) are the partner's responsibility, and the sponsored cards disappear whenever the feed cannot be read. Verify that impressions appear in the TubeCorporate report for this domain after deployment.

## Video pre-roll ads (HilltopAds VAST)

The player shows one linear pre-roll before a video starts, using the HilltopAds Video VAST tag for publisher site 929597. The tag lives in `src/config/vast.ts` (`VAST_TAG_URL`); paste a different zone there, or set the public build variable `INTIMORA_PUBLIC_VAST_TAG_URL`. An explicitly empty value turns pre-roll off. Only HTTPS tags on `surprisedplate.com` / `hilltopads.com` are accepted, and any other value fails the build.

**How it behaves:** the tag is requested once when the player opens, never before the age gate and never for account pages. The creative plays only before the content has started; if the tag has not answered within 1.2 seconds the video starts instead, so an ad server can never block playback. The tag request sends no cookies and no referrer. An empty, failing, malformed or wrapper-looped response simply means "no ad". The skip button appears after the creative's `skipoffset`; a tag without one becomes skippable after 15 seconds, HilltopAds' documented default. Skipping, completing, an ad error, the impression, the quartiles and the click-through tracking are all fired as VAST pixels, and the click-through opens in a new tab with `rel="noopener noreferrer"`. Only plain MP4/WebM linear creatives are supported: VPAID and companion ads are ignored on purpose, so no third-party script or nested frame ever runs on this site. The ad overlay includes its own close button, and closing it closes the player. If the tag cannot be read at all, the build-time snapshot described below still provides a pre-roll.

**CORS is the reason for the published snapshot.** Many ad tags (this one included) answer without `Access-Control-Allow-Origin`, so a browser fetch of the XML is blocked even though the tag itself is healthy; a slow tag can also lose the race against playback. The build therefore requests the tag once, on the server, and publishes the resolved creative as same-origin `/ad-fallback.json`. The player still prefers the live tag — a live answer within 800 ms is used as-is, with the tag's own tracking — and only falls back to the snapshot when the tag cannot be read or answers too slowly. The snapshot's impression, quartile, skip, mute and click pixels are fired by our player exactly like a live ad's, so the campaign still counts the view.

To check a deployment, open `https://<site>/ad-fallback.json`: `"enabled": true` means the build reached the tag and a pre-roll is available even to browsers that cannot read it; `"enabled": false` means the tag is switched off or unreachable at build time. The snapshot holds one creative, so it only changes when the site is rebuilt — the live path keeps rotating creatives whenever a browser is allowed to read the tag. `INTIMORA_AD_PROBE_OFFLINE=1` skips the build-time request (the test suite uses it).

**CORS is the one external dependency.** A browser can only read the tag when the ad server returns `Access-Control-Allow-Origin` for this origin; without it the fetch fails, the ad is skipped silently and the video still plays. This cannot be fixed from the frontend alone — check the Network tab on the deployed site after enabling the zone, and use the HilltopAds dashboard or support if the tag does not answer with CORS headers. No CSP change was needed for pre-roll: the tag request is `connect-src https:`, the creative is `media-src https:` and the tracking pixels are `img-src https:`. Adding VPAID support would require widening `frame-src` and `script-src`, which this implementation deliberately avoids.

The ad unit is third-party inventory: its fill rate, CPM, creative quality and landing pages are controlled by HilltopAds, ad blockers can hide the frame entirely, and the site earns nothing when no ad fills. Confirm that impressions appear in the HilltopAds report for this domain after the first deploy.
