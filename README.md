# Intimora

Intimora is a React + Vite frontend designed to run as a **Render Static Site**. The browser calls the public discovery Worker, reads `data.server` from `{ "ok": true, "data": { "server": "https://…" } }`, and calls that backend directly, appending routes such as `/api/videos`. No proxy is required by the static site.

## Discovery and routing

The existing public Worker is the default. To use a different public endpoint, set `INTIMORA_PUBLIC_API_DISCOVERY_URL` at **build time** (see `.env.example`). It must be an HTTPS URL without credentials, a query string, or a fragment. The build rejects invalid values without printing them. The variable and Worker URL are public, not secrets.

Discovery starts on arrival, including while the age gate is open. Each new browser tab/navigation starts its own discovery; concurrent requests in that tab share it. The selection is cached for at most 60 seconds from the start of discovery, using session storage with an in-memory fallback. Reloading the same tab may reuse its own unexpired selection. A new navigation does not reuse an entry copied from another tab. When it expires, the next request refreshes discovery; videos and pagination cursors already loaded remain pinned to their original backend. Media elements contact that backend directly and support its byte-range responses. Likes and share tracking also use the video's original backend.

The actual pages have stable URLs: `/`, `/trending`, `/new`, `/exclusive`, `/categories`, `/search?q=...`, `/login`, `/profile`, `/referral`, `/dashboard`, and `/watch/<id>`. Navigation links, direct entry, refresh, and browser back/forward restore the corresponding page. Account pages still require the appropriate sign-in/profile state, and all content still waits for the age gate. Search terms are included in the URL, so they may be saved in browser history or server logs, or shared when a search link is copied; do not put secrets in search queries.

Opening a video updates the address to `/watch/<id>`. Shared links do not contain a backend address. A recipient discovers their own backend and opens that ID there. The backends therefore need to serve the same video IDs for links to work across visitors. A missing video or failed request shows a generic message without a server address.

## Streaming and caching

After age confirmation, opening a video mounts one native player with the video's stable, pinned backend URL and poster. The browser handles HTTP ranges and buffering directly: there is no parallel JavaScript downloader, Blob URL, cache-busting query, or media preload for catalog cards. Clicking a card's play button or “Watch Now” attempts to start playback immediately; if the browser blocks it, the regular play button remains available. Shared links do not autoplay after the age gate. The player suggests `preload="auto"` for the selected video and `metadata` when the browser reports data saver or a 2G connection. These are hints, not transfer limits: browsers may ignore them, playback requests buffering regardless of the hint, and `auto` can download the whole selected video. The player indicates buffering, allows retry on errors, and supports click and keyboard seeking. The backend currently offers one source, so the UI does not pretend to switch quality.

A backend response of `Cache-Control: public, max-age=3600` permits browser caching where the browser supports it; it does not ensure a cache hit, a shared cache, or a speed increase. Keep video IDs immutable for that period (or deploy a versioned URL and purge changed content), and return a strong `ETag` for safe range validation and combination. The inspected stream route does not explicitly set one. Vercel's [CDN cache criteria](https://vercel.com/docs/caching/cdn-cache#cacheable-response-criteria) exclude requests containing `Range` and `206` responses; dynamic CDN caching also needs an appropriate shared-cache policy. Do not assume native range requests are served from Vercel's CDN just because `max-age` is present. The browser tests use a cacheable local fixture with a strong ETag; this does not verify either deployed backend.

**Backend streaming checks required:** the inspected backend `main` revision (`17908bae2a17124c838b732b2d1ad28812184b37`) has the same stream source as `5e499b39408397c637b9153b1270f307d1575733`. In local mocks of the extracted `GetFile` path, 17 aligned chunks remained in order with at most eight concurrent calls; unaligned, multi-batch and 13-byte EOF ranges returned exact bytes, using a 512 KiB request limit even at EOF. The extracted route returned `416` with `Content-Range: bytes */<size>` for the tested reversed and unsatisfiable ranges.

Short or empty non-final `GetFile` responses are still silently accepted. A mock returning 42 fewer bytes from a middle part produced the advertised response length but the wrong bytes, because later bytes filled the gap. Validate each returned chunk against the file size and requested interval; retry a missing part at its original offset or abort rather than skipping it. A genuinely short final part is valid when its length matches the remaining file bytes.

The separate fast-start path needs attention. Its `findMoovAtom` still sends a shortened final `GetFile` limit, and `readFileRange(video, 0, 31)` requests an invalid 32-byte limit under Telegram's non-precise rules; strict local mocks rejected these calls. Its scan can start inside `mdat` and miss a tail `moov`. With permissive local mocks and the actual MP4 test fixture, the route misidentified an existing beginning `moov` as a tail atom and returned HTTP 200 with only 2,732 bytes from an 832,606-byte video, omitting `mdat`. Do not return only `ftyp` and `moov` as a complete video; serve the original representation with correct ranges, or fully remux to a consistent fast-start file before upload, adjusting offsets and supporting ranges against that complete representation.

The backend waits for each batch before yielding and does not start the next until that batch is yielded; this is not overlapping prefetch. Its small-file path downloads files under 50 MiB in full before yielding the first bytes. The stream code sets `Vary: Origin, Range`, but `vercel.json` separately sets `Vary: Origin` and specifies `Access-Control-Allow-Origin` twice on the same route; verify final deployed headers and CORS. Actual Telegram behavior, live streaming and first-frame speed remain unverified.

Before deploying, test representative small and large videos on each actual backend. Compare response bodies byte-for-byte for one- and multi-batch ranges, unaligned starts/ends, partial final parts, suffix ranges and ends beyond EOF. Check cancellation/backpressure, CORS, errors, first-frame time and repeat-view caching in target browsers; frontend mocks and backend settings do not verify production behavior.

## Catalog views

The first catalog page is shown immediately; subsequent pages are collected from the same selected backend in the background, with overlapping IDs and repeated terminal cursors handled safely. Trending ranks the collected catalog by numeric view count. New shows all uploads from the visitor's local calendar day, or yesterday's uploads only when today has none; older, future, and undated items are not treated as new. Home includes both normal and exclusive videos. Exclusive uses a public `exclusive: true` flag (also accepting an exact `Exclusive` category or tag when no explicit flag is supplied); an explicit `exclusive: false` takes precedence over labels. The backend must include this metadata in its public response; the frontend cannot infer flags that were not returned. Categories currently shows only a Coming Soon message.

The current backend offers date-ordered pages rather than server-side trending or exclusive queries. To avoid presenting an incomplete ranking as complete, the UI reports a retryable incomplete-catalog state on failed, ambiguous, or excessive pagination. Page requests are capped at 50 items and the scan at 120 pages; large catalogs are better served by dedicated server-side sort/filter endpoints. Entering a feed after the catalog has been idle for a minute refreshes the metadata. Cards render incrementally as the visitor scrolls.

## Security and CORS

Direct access means the discovery response, selected backend URL, API responses and network requests are visible in browser developer tools. **Do not send secrets, tokens, signed URLs, private error details, or other confidential data in public Worker/backend responses or public build variables.** The frontend can filter displayed fields, but it cannot hide a response that the browser has already received. Secrets belong in backend-only environment variables and must not be committed. Public URLs and CORS are not authentication: protect sensitive backend routes with proper authentication, authorization and rate limits. The age gate is not age or identity verification.

Every selectable backend and the Worker must allow the deployed site's exact origin in CORS (or `*` for public, credential-free access). Allow `GET`, `POST`, `HEAD` and `OPTIONS`; permit `Content-Type`, `Authorization`, and `Range` on preflight requests. Thumbnail and stream responses must also allow the origin, including byte-range responses. A stream should support `Range`, `206 Partial Content`, `Content-Range` and `Accept-Ranges`. Discovery and backend fetches omit cookies and referrers; they do not follow API redirects. The separate Google popup uses the visitor's normal Google sign-in session. It accepts only public HTTPS discovery/backend URLs without credentials or query strings and uses the standard video media routes instead of arbitrary third-party media URLs.

The static site's CSP permits HTTPS connections, images and media because discovery can select different public hosts, while restricting scripts to the site and Google's Firebase sign-in script. It also permits the Firebase auth domain and Google Accounts as frames for the popup flow, plus `https://hdzog.com` for the sponsored TubeCorporate campaign iframe. If you change the campaign host, update `PARTNER_EMBED_HOSTS`, the CSP in `server/security.mjs` and `render.yaml`, and the tests together. If all legitimate backend and Worker hosts are known and stable, narrow those HTTPS sources in Render's Content Security Policy. Other security headers and a `no-referrer` policy are included in the Blueprint. CORS is enforced by browsers, not by curl or other servers.

## Google accounts, libraries and referrals

The account circle opens Google popup sign-in (with account selection). After the age gate, Firebase restores the existing session, `/api/auth/verify` checks whether the Firebase UID has an account, and `/api/auth/me` supplies its profile and liked/saved video IDs. New users enter a name, a username, and an optional referral code; both Skip and an empty Finish submit without a referral. Registration and confirmation use the same trusted backend. A temporarily missing record is checked again briefly, and an unconfirmed write shows an error instead of silently looping or pretending the account was saved. Guests who try to like or save are sent to sign-in rather than making local-only changes. Like/save buttons react immediately but display a pending state until confirmed; a failed or uncertain request restores the previous confirmed state and asks the user to refresh/check before retrying. The dashboard displays the stored referral code and matches the user's IDs against the public catalog; it does **not** load video details just to build a library, because the backend counts those requests as views. Videos missing from a partial/outdated catalog are reported as unavailable.

**Public likes and action speed need backend work:** the inspected backend updates the user's like list but not the public video aggregate. Its new per-instance user cache can avoid warm Telegram scans, but actions still wait for a Telegram edit and Firebase lookup; local mocks also exposed failed-write and cross-instance cache consistency risks. The frontend does not manufacture a count or make that server write faster. It can consume a versioned count from an upgraded like response and, once the backend contract is deployed on all hosts, poll visible public counts approximately every five seconds. Polling is **off by default**; only then set `INTIMORA_PUBLIC_LIVE_LIKES=1` at frontend build time. Exact API responses, shared atomic storage, migration, authentication, compatibility and measurement instructions are in [the backend handoff](docs/live-likes-backend.md). Live production performance and cross-user updates remain unverified until the backend and frontend are deployed and tested.

**Backend account persistence:** the previously inspected backend revision `5082669c2b02f942326d5831cf535ee3cc5110f9` passed an object to a Telegram wrapper that expected text. A local test using the backend functions and Teleproto stored `[object Object]` instead of user JSON, so a successful create could not be found by UID. Backend `main` revision `1d538bddaac49dd6d2ece29f66ef24c1fa81e510` changes user and referral writes to pass JSON strings and disables Markdown parsing for those sends and edits. With the current backend source and mocked Telegram storage, Skip, blank Finish, valid referral links and subsequent user lookup passed locally. GitHub reports successful Vercel deployment statuses, but live account persistence and both hosts remain unverified. Ensure both backends share the intended account storage, then test registration, referral links, reload/sign-in, and saved/liked actions with a real account. Existing failed registrations may need to complete the profile again.

Firebase's web app configuration in `src/services/firebase-config.ts` contains public client identifiers, not a service-account credential. Restrict the Firebase API key to the required APIs, review quota limits, and keep actual credentials on the backend. In Firebase Authentication, enable the Google provider and authorize the exact deployed hostname and any development origin; configure the Google consent screen/branding as needed. Browser tests use a mock identity provider; verify the real popup, Google project settings, production CORS (including `Authorization` preflights), token verification, and persistent accounts in a deployed browser. Popup sign-in is used deliberately: redirect sign-in on a different hosting domain needs additional Firebase auth-domain configuration. Do not paste Firebase tokens or service-account credentials into logs or chat.

The Worker still selects the visitor's backend. Bearer tokens are sent only to the **exact** trusted auth origins `https://api-intimora.vercel.app` and `https://intimora-api1.vercel.app`, even if discovery returns a different host. Authenticated video actions remain pinned to the trusted backend that supplied that video. If the actual backend fleet changes, explicitly update the public build-time `INTIMORA_PUBLIC_AUTH_BACKENDS` comma-separated origin allowlist after reviewing each new host; the change is not automatic and the value must not contain secrets. Browser requests omit cookies, disallow redirects, and show generic service errors.

**Backend fixes required:** the current `/api/user/liked` and `/api/user/saved` responses contain raw video storage metadata, so the frontend does not call them. More critically, `/api/user/referrals` returns other users' email, Firebase UID, liked/saved histories, and internal storage IDs. The dashboard therefore does **not** request or display the referral tree by default; hiding fields in the browser would not protect data already delivered over the network. Change that backend endpoint to authorize the requester and return only `data.tree.code`, `direct[]`, and `level2[]` with the minimum public `name`, `username`, `referralCode`, and `referredBy` fields for descendants. Remove emails, UIDs, histories, storage IDs and all other private fields from every descendant, and verify that neither ancestors nor unrelated users are returned. That fix is deployed, so the two-level descendant view is now on by default; set `INTIMORA_PUBLIC_SAFE_REFERRALS=0` at build time to switch it off again if a backend host regresses. Also sanitize own-profile/verification responses to remove internal storage IDs. The backend should enforce case-normalized, atomic username uniqueness, generate collision-checked referral codes with a cryptographic random source, and perform atomic user-record updates across concurrent sessions; the frontend cannot guarantee those properties. A tested safe projection for the backend developer is in [the referral handoff](docs/referral-backend-handoff.md).

The ExoClick verification file `f4423f712c6f1c15fb7fc4c833c8c020.html` is copied unchanged into `public/` and will be available at the root of this Static Site **after deployment**. The supplied `6a97888e-site-verification`, `juicyads-site-verification` and `clckd` meta tags are also included in the static page head. This repository is configured for `intimora.new.tg`; neither the file nor the meta tags are automatically published at the separate `new.tg` apex. That hostname must serve this deployment or have the same verification content added on its own host. After deployment, check the HTML source of the exact hostname requested by the verification provider.

The TrafficPeak link appears in the footer after age confirmation, and a no-JavaScript fallback link is also included in the static HTML. After deployment, verify the link at the exact URL requested by TrafficPeak; the service determines whether it accepts the link.

## Local development

```bash
npm ci
npm run dev           # listens on port 5173
npm test
npm run typecheck
npm run build
```

Ensure the Worker and backends allow the **actual browser origin** in CORS, including a remote development-preview origin if used. `http://localhost:5173` and a proxied preview URL are different origins. There is no development API proxy. If the backend does not allow the preview origin, the preview will show the generic unavailable state until that CORS setting is updated. The development server remains available even when discovery fails.

Browser tests run when Chromium is installed (`npx playwright-core install chromium`) or `CHROMIUM_PATH` points to an existing executable; otherwise browser tests are skipped. The streaming browser tests also use OpenSSL to generate a temporary local TLS certificate, and the MP4 range-seeking test requires H.264 support. The legacy Node server and its proxy regression tests remain in the repository for compatibility, but the static frontend does not use those routes.

## Deploy to the existing Render Static Site

1. Keep the existing Static Site and point it at the deployment branch containing these changes. Set the build command to `npm ci --include=dev && npm run build` and the publish directory to `dist`. Node 20.19+ or a supported Node 22 release is required. No Node start command or proxy secret is needed.
2. The existing public Worker is the default. Only if changing it, set `INTIMORA_PUBLIC_API_DISCOVERY_URL` in Render's build environment and redeploy. This value is deliberately bundled into browser code; never put a secret in it.
3. **A rewrite is still recommended.** In the Render dashboard, open the actual Static Site serving the domain → **Redirects/Rewrites** → Add Rule: Source `/*`, Destination `/index.html`, Action **Rewrite** (not Redirect). Put the fallback after any intentional redirects. `render.yaml` contains this rule for a linked Blueprint, but changing the file alone does **not** configure an existing manually-created or unlinked service. Render does not use a Netlify-style `_redirects` file for these rules. Apply the security headers shown in `render.yaml`, adjusting the CSP sources if appropriate. Direct links work without this rule because of the published files described below; the rule additionally gives every path a `200` response without a rebuild.
4. After the rewrite and deployment are active, directly open and refresh `/dashboard`, `/login`, `/trending`, `/new`, `/exclusive`, `/categories`, `/search?q=test` and a real `/watch/<id>` on both the custom domain and the Render URL. They should return the app HTML with HTTP 200 and keep the original URL; unauthenticated account visits may redirect to sign-in. Check `/robots.txt`, the verification file, and an existing JS/CSS asset too. Render serves existing static files before rewrite rules. The wildcard also returns the app shell for unknown paths and missing assets; if strict HTTP 404s are required for those, use explicit rewrites for every listed page and `/watch/*` instead, including trailing-slash variants.
5. Confirm CORS for the production origin on the Worker and every selected backend, including media/range and POST/OPTIONS responses. Then check the catalog, search, playback, likes, sharing and pagination in a real browser. A generic unavailable message can mean discovery, CORS, backend availability, or network configuration failed; inspect deployment and backend logs privately.

### Direct links without a host rewrite

A static host serves an existing file before it evaluates any rewrite rule, so the build publishes a real HTML file for every page. `/trending`, `/new`, `/exclusive`, `/categories`, `/search`, `/login`, `/profile`, `/referral` and `/dashboard` are written as both `<page>.html` and `<page>/index.html`; every `/watch/<id>` listed in the published sitemap becomes `watch/<id>.html` and `watch/<id>/index.html`; and `404.html` holds the same app shell. Each file is a copy of the built `index.html` (roughly 2.4 KB before compression), and the video list is capped at 500 IDs per build.

Opening a page this way still runs the identical app: the age gate, account redirects, search-term handling and `/watch/<id>` detail loading all read the browser's real path. A video uploaded after the build has no shell yet, so its link is answered by `404.html` with a `404` status: the app still opens that video, but search engines may treat the response as missing and some link previews can be less reliable. Rebuild the site (the daily sitemap workflow already does) or add the wildcard rewrite to publish shells for new videos with a `200` status. Unknown paths also receive `404.html`, so they load the app instead of a bare host error page; this is a soft 404.

Local changes and tests do not configure or deploy the existing Render service. Rotate any credentials that were previously exposed or committed and review the backend's public responses before deployment.

## Sitemap and Google Search Console

The site publishes one XML sitemap at `https://intimora.new.tg/sitemap.xml` and advertises it in `/robots.txt`. The checked-in fallback is a snapshot of the home page and public video links available when this change was prepared. During a production build, Vite reads the **public** discovery endpoint and its selected backend's catalog, replacing that snapshot with valid `/watch/<id>` URLs for normal and exclusive videos. It follows overlapping pages, deduplicates IDs, and caps the scan at 120 pages of 50 with a 60-second overall deadline. The sitemap contains site URLs only, not backend addresses, titles, or private data. If discovery, a page, or the scan fails, the build logs a generic warning and retains the checked-in snapshot, which may be out of date; check the published XML and build log after deployment. A repeated full page is treated as incomplete because the backend's cursor can conceal items with the same timestamp.

Render is a Static Site: the sitemap is a **build-time snapshot**, not a live endpoint. New uploads and removals appear at the next successful deploy/rebuild, not immediately. To update it manually, redeploy the existing static site. An optional workflow at `.github/workflows/refresh-sitemap.yml` can request a rebuild daily at 02:17 UTC (GitHub schedules may be delayed):

1. In the existing Render Static Site's Settings, find its deploy hook. Treat this URL as a secret.
2. In the GitHub repository's Settings → Secrets and variables → Actions, add it as the repository secret `INTIMORA_SITEMAP_DEPLOY_HOOK_URL`. **Never commit it or paste it into chat.**
3. Enable GitHub Actions on the default `master` branch. The workflow also supports a manual run. Without the secret it safely skips; with it, each run requests a Render deploy and consumes build minutes.

After the changed branch is merged and deployed, open `/sitemap.xml` and `/robots.txt` to confirm they return the expected files. In the verified Google Search Console property for `https://intimora.new.tg/`, open **Indexing → Sitemaps**, enter `sitemap.xml`, and select **Submit**. A sitemap is a discovery hint, not an indexing or ranking guarantee. The age gate remains in place and the watch content loads only after a visitor confirms their age; Google may therefore be unable to see or index individual videos. Use URL Inspection and Google's [video SEO guidance](https://developers.google.com/search/docs/appearance/video) to diagnose this without weakening the gate.

## Sponsored partner videos (TubeCorporate)

Partner videos are **part of the catalogue layout**: every fourth card is followed by one sponsored card ("four of ours, then one of theirs") on Home, Trending, New and Exclusive. Each sponsored card uses the site's own card markup, outline, hover and typography, and the badge slot that shows `EXCLUSIVE` on our videos shows `SPONSORED` on theirs. Titles and posters come from the partner page itself (`og:title`, `og:image`), so a sponsored card looks like one of our own.

Clicking a sponsored card opens **our player** — the same full-screen overlay, frame and close control as any other video — with the partner's player inside the frame. No pre-roll, no like/save and no related-video logic runs for sponsored content, and nothing appears in search results, on account pages, before the age gate, or on the watch page.

The value lives in exactly one place: `PARTNER_EMBED_URL` in `src/config/partner-embed.ts`. Two shapes are accepted:

1. **A single video embed page**, e.g. `https://desi-porntube.com/embed/762647/?source=1849513610` — rendered as one iframe at the bottom of browse pages.
2. **A campaign CSV feed**, i.e. the "feeds" link from the TubeCorporate dashboard, e.g. `https://desiporn.tube/admin/feeds/embed/?categories=…&source=1849513610&feed_format=csv&tag=girls&csv_separator=%7C&csv_columns=embed`. Each row is a ready-made `<iframe src="…">` snippet, **not** a web page: framing the feed URL itself would only show raw CSV. The build reads it once, extracts the `src` of every iframe, re-validates each URL, drops duplicates and caps the list at 60; the first twelve are then read individually to pick up their title and poster, and the result is published as same-origin `/partner-feed.json` (`version: 2`, one object per video).

**Nothing third-party is contacted before the age gate.** The client reads only `/partner-feed.json` from its own origin — once, after age confirmation — so the feed host needs no CORS headers. If the feed cannot be read (host down, empty, no usable rows, timeout), the build logs `Sponsored feed could not be read` and the sponsored cards are simply absent; the site still ships.

`src/services/partner-embed.mjs` validates both shapes before they are used: HTTPS only, no credentials or fragment, an `hdzog.com`, `tubecorporate.com` or `desi-porntube.com` host for embeds, a `desiporn.tube` / `desi-porn.tube` host for feeds, an `/embed/<id>` path for feed rows, and a numeric `source` parameter (appended automatically when the pasted URL omits it). An unknown host, a non-HTTPS URL or an unsafe query fails the build, so a mistyped value cannot ship. `src/services/partner-cards.mjs` validates the published cards again, and `npm test` covers both shapes, the mixing rule and the player.

**Where to change it:** edit the single `PARTNER_EMBED_URL` line in `src/config/partner-embed.ts`, save and commit; the build picks the shape automatically. The public build variable `INTIMORA_PUBLIC_PARTNER_EMBED_URL` overrides the file (it is bundled into browser code, so never put a secret there), `INTIMORA_PARTNER_FEED_TIMEOUT_MS` (500–60000, default 10000) bounds the build-time feed request, and `INTIMORA_PARTNER_FEED_OFFLINE=1` skips the fetch entirely — the test suite uses it so tests never contact the campaign host. The CSP allows frames from `hdzog.com` and `desi-porntube.com` only.

Third-party content stays outside this site's control: ad blockers can hide the cards, the campaign's own availability, cookies, creative quality and anything its player overlays (including its own branding) are the partner's responsibility, and the sponsored cards disappear whenever the feed cannot be read. Verify that impressions appear in the TubeCorporate report for this domain after deployment.

## Video pre-roll ads (HilltopAds VAST)

The player shows one linear pre-roll before a video starts, using the HilltopAds Video VAST tag for publisher site 929597. The tag lives in `src/config/vast.ts` (`VAST_TAG_URL`); paste a different zone there, or set the public build variable `INTIMORA_PUBLIC_VAST_TAG_URL`. An explicitly empty value turns pre-roll off. Only HTTPS tags on `surprisedplate.com` / `hilltopads.com` are accepted, and any other value fails the build.

**How it behaves:** the tag is requested once when the player opens, never before the age gate and never for account pages. The creative plays only before the content has started; if the tag has not answered within 1.2 seconds the video starts instead, so an ad server can never block playback. The tag request sends no cookies and no referrer. An empty, failing, malformed or wrapper-looped response simply means "no ad". The skip button appears after the creative's `skipoffset`; a tag without one becomes skippable after 15 seconds, HilltopAds' documented default. Skipping, completing, an ad error, the impression, the quartiles and the click-through tracking are all fired as VAST pixels, and the click-through opens in a new tab with `rel="noopener noreferrer"`. Only plain MP4/WebM linear creatives are supported: VPAID and companion ads are ignored on purpose, so no third-party script or nested frame ever runs on this site. The ad overlay includes its own close button, and closing it closes the player. If the tag cannot be read at all, the build-time snapshot described below still provides a pre-roll.

**CORS is the reason for the published snapshot.** Many ad tags (this one included) answer without `Access-Control-Allow-Origin`, so a browser fetch of the XML is blocked even though the tag itself is healthy; a slow tag can also lose the race against playback. The build therefore requests the tag once, on the server, and publishes the resolved creative as same-origin `/ad-fallback.json`. The player still prefers the live tag — a live answer within 800 ms is used as-is, with the tag's own tracking — and only falls back to the snapshot when the tag cannot be read or answers too slowly. The snapshot's impression, quartile, skip, mute and click pixels are fired by our player exactly like a live ad's, so the campaign still counts the view.

To check a deployment, open `https://<site>/ad-fallback.json`: `"enabled": true` means the build reached the tag and a pre-roll is available even to browsers that cannot read it; `"enabled": false` means the tag is switched off or unreachable at build time. The snapshot holds one creative, so it only changes when the site is rebuilt — the live path keeps rotating creatives whenever a browser is allowed to read the tag. `INTIMORA_AD_PROBE_OFFLINE=1` skips the build-time request (the test suite uses it).

**CORS is the one external dependency.** A browser can only read the tag when the ad server returns `Access-Control-Allow-Origin` for this origin; without it the fetch fails, the ad is skipped silently and the video still plays. This cannot be fixed from the frontend alone — check the Network tab on the deployed site after enabling the zone, and use the HilltopAds dashboard or support if the tag does not answer with CORS headers. No CSP change was needed for pre-roll: the tag request is `connect-src https:`, the creative is `media-src https:` and the tracking pixels are `img-src https:`. Adding VPAID support would require widening `frame-src` and `script-src`, which this implementation deliberately avoids.

The ad unit is third-party inventory: its fill rate, CPM, creative quality and landing pages are controlled by HilltopAds, ad blockers can hide the frame entirely, and the site earns nothing when no ad fills. Confirm that impressions appear in the HilltopAds report for this domain after the first deploy.

## Search appearance and branding

The home page provides `WebSite` structured data and an `og:site_name` of **Intimora**. The diamond favicon has explicit 16- and 32-pixel PNGs for browser tabs, a stable 192-pixel PNG for search, and ICO and Apple touch icon variants. The on-site wordmark uses the locally hosted Dancing Script font; its OFL license is in `public/licenses/`. `public/logo.svg` is the master mark: when changing it, regenerate `logo.png`, `favicon-16.png`, `favicon-32.png`, `favicon-192.png`, `favicon.ico`, and `apple-touch-icon.png` to keep them consistent.

After deploying, verify that the home page, `/robots.txt`, and `/favicon-192.png` return 200 and are accessible to Googlebot and Googlebot-Image, including through any CDN or firewall. Browser favicons can remain cached: try a hard refresh or a private window after deployment if the old tab icon remains. In Google Search Console, use URL Inspection on `https://intimora.new.tg/` and request indexing. Google determines the displayed site name, favicon, and search-result font; changes can take days or weeks after recrawling and are not guaranteed. See Google's [site-name](https://developers.google.com/search/docs/appearance/site-names) and [favicon](https://developers.google.com/search/docs/appearance/favicon-in-search) guidance.
